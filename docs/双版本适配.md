# 双版本适配

基于 Xuyuha/LibraryOfRuinaLib `f9585913b231cca2072864825d36483052085737`（1.3.1），并合入上游 `e94028a` 的清单更新。清单 `author` 沿用上游 `e94028a` 的原串 `Natsuki, Nanoka, Ayin, Hod?...`，双版本适配不改动署名。新增可复现工程文件，分别构建 0.107.1 和 0.111.0 实现。上游 1.3.2 仍要求 0.111.0，因此双版本发行使用 1.3.3，最低游戏版本为 0.107.1。

原 1.3.1 源码在正确引用旧版后出现 19 个首批编译错误；不能靠把 min_game_version 改低获得兼容。MSBuild 曾优先选择工程 `libs/sts2.dll` 导致假通过，现禁用 CandidateAssemblyFiles。

## 差异表

| 原版变化 | 影响 | 处理 |
| --- | --- | --- |
| 伤害增量/倍率/上限增加 CardPlay | 力量覆写和 LibraryHooks 转发 | 覆写签名编译切换；原版调用放到 GameApi 分部文件。自定义库接口仍接收 CardPlay，旧原版回调没有该对象时传 null |
| CardLocation 替代 PileType/CardPilePosition 元组 | LibraryMultipleModePower / LibraryPowerMode | 按目标提供完整分部文件，保留模式及子类转发 |
| AfterBlockBroken 新增上下文与破盾者 | 原版覆写与多模式转发 | 使用对应目标的签名；库自有完整上下文接口继续保留 |
| AttackCommand.FromCard / FromOsty、CreatureCmd.Damage 参数变化 | 攻击和伤害命令、预览 | GameApi 分部封装，Harmony 损伤目标按参数列表编译 |
| Hook.AfterSideTurnEnd 旧名为 AfterTurnEnd | 回合结束清理补丁 | 按目标声明 Harmony 方法名 |
| Mod.assembly / assemblies | 网络类型登记的程序集枚举 | 分版本枚举；加载器保证选中的实现参与模型发现 |
| 初始化 DLL 位于 lib/<目标>/ | 资源包定位 | 从实现所在目录回到发行根目录寻找共享 PCK |
| 历史 STS2_BETA 隐藏了 5 个覆写 | 金币、力量数量和关键词转发被漏编译 | 反编译确认两个目标均有对应签名，移除旧条件并在两个目标正常覆写 |

除覆写签名与补丁声明外，API 差异均在整个文件被 `#if` 包住的分部实现。数值、模型 ID、持久化字段和补丁所有者不随目标改变。

## 构建

```bash
dotnet build LibraryLib.csproj -c Release -p:CompatibilityTarget=0.107.1
dotnet build LibraryLib.csproj -c Release -p:CompatibilityTarget=0.111.0
python3 tools/build_dual.py --pck /绝对路径/LibraryOfRuinaLib.pck
```

需要 .NET 9。`CompatibilityTarget` 默认 0.111.0，只允许两个目标值。引用根目录可用 `-p:GameRefsRoot=...` 或打包脚本 `--refs` 指定，默认 `~/sts2-mods/HextechRunes/versioned-dll-backups`；其下必须有 `<目标>/game-refs`。工程不依赖父目录的构建配置，不需要修改或检出第三方分支的构建脚本。

工程使用 `Godot.NET.Sdk/4.5.1`（首次构建需要 NuGet 中的 Godot.NET.Sdk 与 Godot.SourceGenerators 4.5.1），以便源码生成器为速度骰界面、目标线和伤害/治疗数字等 Node 子类生成 `MethodName`/`PropertyName`/`SignalName`、`InvokeGodotClassMethod` 覆写、`ScriptPath` 和 `GodotPlugins.Game.Main`；改用普通 `Microsoft.NET.Sdk` 同样零错误，但引擎不会再回调这些类型的 `_Ready`/`_Process`/`_Draw`。SDK 自带的 NuGet GodotSharp 已关闭，GodotSharp 与 sts2、0Harmony 一样只取 `<目标>/game-refs`，可用 `dotnet msbuild LibraryLib.csproj -t:ResolveReferences -getItem:ReferencePath -p:CompatibilityTarget=<目标>` 核对。仓库没有 project.godot，生成器不需要它；`GodotProjectDir` 取默认的工程目录，`ScriptPath` 因此是 `res://SpeedDice/LibrarySpeedDiceUi.cs` 这类相对仓库根的路径，与 1.3.1 发行版一致。若移动工程文件或改写 `GodotProjectDir`，这些路径会随之改变。

实现输出：`build/bin/LibraryLib/<目标>/Release/net9.0/LibraryOfRuinaLib.dll`。不要让下游编译引用发行根目录的加载器。`build_dual.py` 在打包时用 `tools/GodotGeneratedCheck` 检查两个变体的生成代码，缺失即失败。

```text
build/dual-release/LibraryOfRuinaLib/
├── LibraryOfRuinaLib.json
├── LibraryOfRuinaLib.dll             # 身份为 LibraryOfRuinaLib.Loader
├── LibraryOfRuinaLib.pck             # 两个目标只用这一份
├── libraryofruinalib-variants.manifest
├── bundle-evidence.json
└── lib/
    ├── 0.107.1/{LibraryOfRuinaLib.dll, compat-target.txt}
    └── 0.111.0/{LibraryOfRuinaLib.dll, compat-target.txt}
```

PCK 内容未修改，验证使用 1.3.1 发行 PCK。加载器固定引用 0.107.1，选择不高于宿主的最新变体；未知宿主和损坏清单失败。0.111.0 使用 AssociateAssemblyWithMod；0.107.1 等检测完成再改写 Mod.assembly 并初始化，追加已缓存的实现类型。文件哈希、程序集身份及目标元数据都要匹配。

## 验证与限制

- 两个实现零错误编译，各保留 5 项原有警告；加载器零错误编译。非法目标值会直接失败。
- 两目标清单完全一致：21 个模型、0 个 SavedProperty、91 个补丁类、188 个常量字段；源码数值清单一致。元数据证据位于 `snapshots/<目标>/`。改用 Godot SDK 后这五份清单不变；IL 数值清单只新增 7 个 Godot 脚本类型的生成方法和 `GodotPlugins.Game.Main`。
- 两个变体的生成类型集合与 6 个 `ScriptPath` 值和工坊 1.3.1 发行 DLL 相同。
- 两目标静态 Harmony 目标及按名称注入参数解析成功；另有 3 个动态目标类。
- 加载器 11 项离线选择与拒绝损坏检查通过。
- 0.111.0 在 APFS 游戏克隆、隔离 HOME、`--headless --force-steam=off`，仅与 RitsuLib 0.6.2、ActLikeIt2 0.2.3、LibraryOfRuina 0.22.7 一起加载。日志确认 0.111.0 实现、官方程序集关联、基础库初始化和资源包挂载成功；实际补丁表覆盖 91/91 个类，共 100 个补丁方法记录。这次加载使用的是改用 Godot SDK 之前、缺少生成代码的构建；当前构建尚未做运行时加载验证，速度骰界面等节点的回调恢复只有元数据证据。
- **0.107.1 未做运行时加载验证**。没有验证实际伤害结算、混乱系统、速度骰、旧存档读写或双客户端联机；不能把编译和清单比对当作这些场景通过。

配套本体仓库 `tools/compare_dual.py`、`tools/DualTargetAudit` 和 `tools/LoaderContractCheck` 提供离线核对命令。只提交 PR；未合并、发布或上传工坊。
